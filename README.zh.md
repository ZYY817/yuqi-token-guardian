# Token Guardian —— 已归档

**状态：已废弃。** 建立在一个错误前提上，保留公开作为复盘记录。
实测证据见 [POSTMORTEM.md](POSTMORTEM.md)。

一个 DeepSeek Harness（dsh）插件，曾试图解决 DeepSeek 的思考失控——
模型打转数小时、烧掉几千万 token 的失效形态——手段是压缩回放的
`reasoning_content`、去重工具结果、给机械步降思考档位。

## 为什么失败

- **保险丝不敢拉闸。** 唯一能制止失控的手段——token 硬顶和打转检测——
  被做成了默认关闭和建议性提醒。一个不收敛的模型不会理会"请收敛"的
  提示。整套方案里不存在"物理终止一个正在烧钱的会话"的能力：这个问题
  唯一需要的东西，恰恰是唯一被刻意排除的东西。
- **指标选错。** 头条数字 −98.6% 统计的是"回放字符数"——这部分按前缀
  缓存价计费（实测命中率 ~93%）。真实账单收益从未被证明；网关路由上的
  消融实验没有可归因的 token 差异。
- **核心机制负收益。** 会话中途切换 effort 会改变请求前缀——实测每次
  换挡 `cached_tokens=0`。长会话上一次换挡把全部历史按全价重算，只为省
  几百个缓存价 token。
- **层选错。** 思维链回放是 harness 序列化层的策略问题，正确的修复位置
  在上游或 HTTP 代理层，而不是绑在 rc 版工具内部 API 上的插件。
- **前提在开发环境中不成立。** 开发用网关本来就剥掉思维链再转发、也无法
  区分 effort 档位。这个事实在插件写完**之后**才发现——计划写明
  "探测先行"，实际没做到。

## 仍然成立的部分

- `sweep`：把已完成的"思维链+工具调用"整组替换为摘要（操作点靠近历史
  尾部）。官方路由实测：`reasoning_content` 归零、全部 200、缓存命中
  ~93%。
- `max_tokens` 保险丝：对失控思考是真实有效的物理截断，实测精确截在
  封顶值。
- 成本模型：`未命中前缀×全价 + 命中前缀×缓存价 + 输出×全价`。
  优化优先级 = 减少往返 > 保持前缀稳定 > 裁剪内容。

## 如果你真的遇到这个问题

不要装这个插件。把 `reasoningEffort` 调到 low/medium，再设一个
`max_tokens` 上限——两行配置覆盖真实账单的大头。
